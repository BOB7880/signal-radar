# 信息过载时代的个人信息决策雷达：从信息筛选到可验证行动

作者：半肥猫 · 紫鲸 AI  · [www.zjai.ink](https://www.zjai.ink) · 公众号：半肥猫 AI研习社

## 摘要

AI 工具降低了搜索、摘要和生成内容的成本，却没有同步降低判断与验证的成本。使用者因此面对一个新的矛盾：信息更容易获得，值得投入注意力的信息却更难辨认。GitHub Trending、社交媒体、行业文章、产品发布和研究论文都可以在短时间内进入个人视野，但“热度”“表达强度”与“对我有用且经得起核查”并非同一件事。

本文把个人信息筛选定义为一种**在不确定性下分配稀缺注意力与验证预算的决策问题**。文章从信息过载与有限认知出发，区分信息相关性和证据可信度，提出“个人信息决策雷达”：先设业务目标，再采集和去重，建立来源与证据链，分轴评分，按风险分级推送，通过小实验验证，最后用用户反馈校准系统。文中给出一套可执行的评分机制、运行架构、四周评估方案，并比较五个公开 GitHub 项目。末尾附上一份可移植的 Skill 草案。

**关键词：** 信息过载；注意力分配；证据核验；个性化推荐；AI Agent；知识管理；决策支持

## 一、痛点发现：每天都在信息洪流里做选择

你有没有过这样的早晨：刚打开手机，工作群、公众号、社交平台和 GitHub 已经堆来一长串更新。你知道里面可能有值得关注的行业变化、工具或方法；不看，担心错过机会；逐条点开，又要读原文、查来源、分辨宣传和事实，遇到软件项目还想亲手跑一遍才敢判断。等忙完一轮，半天已经过去，真正能落到手头业务上的内容却未必有几条。

更难的是，标题常常比证据跑得快。一个新项目被说成“颠覆工作流”，点进去可能只有概念框架；一个传播很广的说法，追到最后却找不到原始数据。于是人陷入两难：不查，害怕漏掉重要信息；全查，又没有足够的时间和精力。

这段情景来自本文作者对日常信息获取与验证负担的观察，是研究问题的起点，不是代表性调查结果。它引出本文关注的更具体问题：**当信息不断涌入、人工核验预算有限时，怎样把有限注意力优先分配给更可能相关、且证据足以支持下一步行动的内容？**

信息雷达也可能成为新的收件箱。若系统每天固定推送十条摘要，却仍让用户逐条判断“为什么值得看、依据在哪里、下一步如何低成本验证”，它只压缩了文字，没有减少决策负担。因此，本文不把“总结更多内容”当作目标，而是把目标设为：减少无效阅读，同时保留发现重要机会与风险的能力。

本文提出的是一套可检验的设计方案，而非已被证明普遍有效的算法。评分权重、推送阈值和效果指标都应作为**待验证的设计假设**。

## 二、底层逻辑：稀缺的不是内容，而是注意力与验证能力

### 2.1 信息供给增加，不等于决策能力增加

信息过载研究讨论的核心并不是单纯的数量，而是输入超过接收者在给定时间和认知条件下处理、区分与使用信息的能力。组织与管理研究也指出，信息环境会竞争注意力，并可能增加搜集、储存、分享和筛选成本，使人偏离与当前目标相关的任务。[信息、注意力与决策研究](https://journals.aom.org/doi/10.5465/amj.2015.4003)

在生成式 AI 普及后，采集和摘要可以变便宜，但这并不意味着核查更便宜。恰恰相反，内容生成的边际成本下降，会让未经证实的解释、宣传文案和二手转述更容易进入信息流。系统若以摘要数量、覆盖源数量或“看起来全面”作为成功指标，容易把供给端的增长误当成用户价值的增长。

### 2.2 这是一个注意力预算分配问题

可以把用户一天的可用注意力记为 (A)，每条候选信息 (i) 所需阅读与验证成本记为 (C_i)，其可能带来的业务收益、风险避免或学习收益记为 (V_i)。用户真正要处理的不是“是否收集到更多条目”，而是如何在有限预算内选择信息集合 (S)：提高预期相关价值，控制阅读与验证成本，为低概率高损失事件保留独立通道，并给新主题留出探索空间。

这与背包式资源分配相似，但候选信息的价值和可信度都不确定；因此需要把“相关性排序”与“证据判断”分开，还要留出人工复核和小规模验证环节。

### 2.3 可信度不能由表达自信程度替代

标题和摘要通常是信息源最擅长说服读者的部分，却不是核实事实的充分材料。评估科学错误信息的研究讨论了“横向阅读”：读者离开当前页面，到独立来源查询发布者、证据与其他报道，而不是只在原站内部阅读更多自我陈述。[相关实验研究](https://pmc.ncbi.nlm.nih.gov/articles/PMC8981191/)

将这一做法转化为 AI 雷达的规则，就是把每个重要主张拆成：

- **主张：** 来源到底声称了什么？
- **一手证据：** 官方文档、代码、发布记录、数据集、论文或实际演示在哪里？
- **独立佐证：** 是否存在与作者无直接利益关系的复现、评测或报道？
- **限制条件：** 证据能支持到什么程度，哪些部分仍只是作者自述？
- **时效：** 证据对应哪个版本、日期和环境？

这样可以避免把“有人说某项目很强”自动转写为“项目已被证明很好用”。

### 2.4 推荐还需要探索，避免个人信息茧房

如果系统只学习用户过去点击过什么，它会倾向于重复用户熟悉的主题和来源。相关推荐系统研究指出，相关性、多样性和一定程度的随机探索需要共同考虑；只把相似度最大化，可能损害偶然发现新方向的机会。[“Uncovering Recommendation Serendipity with Objective Data-driven Factor Investigation”](https://doi.org/10.1145/3758092), *ACM Transactions on Information Systems* (2025).

因此，一个成熟的信息雷达既要知道用户关注什么，也要保留少量“邻近主题”探索位，并对法规、安全、重大故障等高损失信息设置独立通道。

## 三、形成的逻辑：从“摘要机器”转向“注意力决策支持”

本文把系统目标定义为：**以可追溯证据减少用户做出下一步判断所需的时间，同时控制误报与漏报成本。**

这一定义导出四个设计原则：

1. **先有目标，再采集。** 信息源不能替代业务定位。先写明用户近期目标、长期方向、排除项和可投入时间。
2. **把“对我有用”与“它是否可信”拆开。** 很相关但证据弱的信息可以进入观察队列；可信但无关的信息可以归档；二者都高才适合进入实验队列。
3. **推送是稀缺额度。** 日报不是固定填满。没有达到阈值时允许安静；高风险事项另行告警。
4. **每条推荐都通向一个低成本验证动作。** 从“看起来不错”转为“30 分钟能否验证最关键的假设”。

## 四、个人信息决策雷达：评分、筛选与证据机制

### 4.1 先设安全与使用门槛，评分不能抵消风险

发现和使用是两个不同决定。来源或许可证不清的项目仍可作为“待核验线索”出现，但不能被描述为可复用、可部署或适合生产；遇到不安全安装方式，应停止运行并只报告风险。对软件项目、技术文章和工具建议，先检查：

- 来源身份、原始链接和发布时间可确认；
- 代码项目的许可状态明确，或明确标为“许可未知/暂不用于生产”；
- 安装和下载方式可解释，依赖与权限没有显著异常；
- 项目未归档，或即使归档也有明确的历史研究价值；
- 涉及账号、数据、金钱或对外发布的动作，默认只给建议，未经授权不执行。

使用门槛未通过时，不允许高相关度把风险“打分救回来”。系统可以保留一条带警示的发现记录，但不能建议用户安装、运行、复用代码或放进生产环境，除非相关许可和安全问题已解决。

### 4.2 双轴评分：价值相关性与证据可信度

建议所有维度按 0–5 分打分。初始权重是可调整的起点，并非经过普遍验证的行业标准。

**A. 价值相关性 (R)：**

| 维度 | 权重 | 判断问题 |
|---|---:|---|
| 战略匹配 | 35% | 是否直接支持用户当前业务目标或明确的长期方向？ |
| 潜在影响 | 25% | 如果属实，会改变决策、降低成本或产生收入吗？ |
| 新颖性 | 15% | 与近期已看内容相比，是否带来新事实、新版本或新方法？ |
| 可行动性 | 20% | 是否能在可接受时间和资源内验证或采用？ |
| 视野多样性 | 5% | 是否补充了不同来源、领域或观点？ |

归一化后：

`R = 20 × (0.35S + 0.25I + 0.15N + 0.20A + 0.05D)`

其中每个维度取 0–5 分，结果范围为 0–100。(R) 只估计与用户目标的相关性、影响潜力和行动成本，不表示信息为真的概率。证据状况另用 (T) 标签描述，避免把同一证据在总分里重复加权。

**B. 证据等级 (T)（可核验程度）：**

| 等级 | 说明 | 常见依据 |
|---|---|---|
| T0 未核验 | 只有转述、标题或无法访问的说法 | 社媒二手截图、无出处观点 |
| T1 来源自述 | 可确认作者或项目方确实这样宣称 | 官方 README、产品公告 |
| T2 可检查产物 | 有代码、文档、版本记录、数据或可运行演示 | 仓库、测试、发布包、公开 API |
| T3 独立佐证 | 有独立复现、外部评测或多源一致证据 | 非作者评测、独立用户报告 |
| T4 多条件复现 | 在明确环境下由多个独立来源重复验证 | 可复现实验、多个独立部署案例 |

证据等级 T0–T4 是序数标签，不是事实正确概率，也不能当作等距分数相加。T 越高，表示公开材料中可检查的证据链与独立复现程度越高；它仍不能证明内容必然适配个人业务。

**推送规则建议：**

- `R ≥ 75 且 T ≥ T2`：进入本周精选；
- `R ≥ 75 且 T < T2`：标注“高潜力、待核验”，不写成确定结论；
- `R 55–74`：进入观察区或周末汇总，不即时打扰；
- `R < 55`：默认归档；
- 安全、合规、账号泄露、重大故障等高损失事件：走风险通道，不受一般推荐阈值限制。

初期可按每周最多 5 条精选、每条最多 1 个主实验控制阅读负担；用户反馈后调整，不追求每日凑满。

### 4.3 来源核验与主张拆分

对高影响信息执行“主张—证据—限制”核验：

1. 摘出最重要的一个可验证主张；
2. 找原始材料，优先项目官方文档、代码、版本记录、原始数据或论文；
3. 查至少一个独立来源，或者明确写“暂无独立佐证”；
4. 核对时间、版本、适用条件和利益关系；
5. 将可观察事实与系统推断分开写；
6. 给每条结论附可点击出处，无法确认时写不确定性。

例如，一个 GitHub 仓库的星标增长只能支持“关注度增加”这一事实，不能单独证明“性能领先”“生产可用”或“适合紫鲸”。README 可以证明作者声称支持某能力；代码、测试和可复现实验才能进一步支持能力是否存在；真实业务适配还需本地验证。

### 4.4 三级验证漏斗：把验证成本封顶

- **一级：约 2 分钟元信息筛查。** 看来源、日期、许可、最近更新、是否有真实产物、是否重复。
- **二级：约 10 分钟证据检查。** 看文档、代码入口、测试、版本记录、演示和独立佐证，写出一条主要风险。
- **三级：30–90 分钟沙盒实验。** 只验证一个核心假设，使用合成或脱敏数据；记录环境、步骤、结果、失败点和复现成本。

只有三级实验通过后才进入“试点/采用”讨论。任何涉及生产账号、真实客户信息、扣费、发布或不可逆操作，都需要单独审批与回滚设计。

### 4.5 用分流队列减少打扰

- **立即告警：** 可信度较高、潜在损失大且有时效性的安全或业务事件；
- **每周精选：** 高相关且有最低证据支撑的机会；
- **实验候选：** 有吸引力但仍需验证，附一个限时实验；
- **观察与归档：** 低优先、重复、过期或证据不足条目。

系统应允许“今天没有值得推送的内容”。安静不是失败，而是可能意味着筛选器成功挡住了噪声。

## 五、系统实现：Skill、连接器、状态与调度各司其职

一个可运行系统至少包含以下模块：

1. **用户画像：** 业务目标、用户角色、产品边界、目标受众、时间预算、风险偏好和不关注主题；
2. **采集连接器：** RSS、GitHub API/公开页面、公告、论文、社区等；遵守网站条款、频率限制与隐私要求；
3. **规范化和去重：** URL 规范化、内容指纹、主题聚类、已读和版本变化状态；
4. **证据包：** 原始链接、作者、发布时间、抓取时间、版本、主张、引用片段与佐证关系；
5. **筛选与评分：** 硬门槛、双轴分数、阈值、队列、摘要和实验建议；
6. **状态与反馈：** 用户看了没有、是否值得、是否尝试、实验结果、误报/漏报修正；
7. **调度与交付：** 定时运行、重试、通知、知识库落盘和故障告警。

Skill（如 `SKILL.md`）适合承载工作方法、判断规则、输出格式和工具调用步骤；它本身通常不提供稳定的定时唤醒、数据源访问、数据库或消息投递。官方 Skill 文档也将 Skill 定义为可复用的指令与资源能力层；实际调度和连接器需由所在平台或外部运行环境提供。[OpenAI Skills 文档](https://developers.openai.com/plugins/concepts/skills)；[Scheduled Automations 文档](https://developers.openai.com/api/docs/guides/agents-api/sessions/automations)

因此，更可移植的实现是：**一份平台无关的 Skill + 一份用户画像配置 + 一组来源连接器 + 可持久化状态 + 调度器 + 消息通道。** Claude Code Routines、Codex/ChatGPT 的定时任务、OpenClaw Cron 或系统级定时器可以承担调度，但每种环境的工具权限、凭证、网络与交付机制需要单独配置。不能把“装了 Skill”误认为“系统已经每天自动工作”。

## 六、五个相近 GitHub 项目：能借鉴什么，不能据此推断什么

下表是截至 **2026-11-15** 对公开仓库说明与文档的快速比较，目的是按本文问题的适配度挑选参考，不是按 GitHub 全站星标做的客观排名，也没有在本机完整部署五个项目。成熟度判断因此是桌面研究，不等于生产验证。

为了让“前五”可解释，本文按四项维度进行桌面初筛：个人化雷达匹配度 40%、证据与来源可追溯性 25%、自动化与状态管理 20%、上手及复用条件 15%。每项 0–5 分，按权重加总。下表是对公开 README、文档、许可文件和可见仓库结构的定性评估，未完整部署或审计代码；因此只用于选阅读对象，不是 GitHub 全站排行榜或产品质量认证。对 `ai-news-digest`，GitHub 公开页当前未见 LICENSE，复用条件分因此较低，下载代码不等于获准再分发。

### 6.1 推荐的阅读顺序

## 七、验证方案：用四周试点检查“是否可能省时间”

### 7.1 预先定义的试点问题

- 系统能否减少用户每周阅读与筛选时间？
- 每周精选中，用户认为值得投入时间的比例是否足够高？
- 有没有漏掉会改变业务决策的重要信息？
- 用户能否从摘要快速追溯到原始证据？
- 推荐是否产生了真实实验或行动，而非仅仅增加收藏？

### 7.2 试点设计

这是一项形成性可行性试点，不足以单独证明雷达导致了效率提升。四周内来源和事件会变动，参与者也知道自己在使用筛选系统。若要估计因果效果，应扩大周期并采用预先定义的轮换/对照设计。

**第 1 周：基线。** 维持现有搜集方式，记录每天候选数量、实际阅读时间、认为有价值的条目、采取行动及遗漏事件。不要求把所有内容全部阅读，可抽样记录。

**第 2–3 周：雷达运行。** 选 3–5 个有代表性的来源和 2–3 个具体业务目标。每周最多推送 5 条，执行两级核验；只对 1–2 条做 30–90 分钟沙盒实验。保存分数、证据包、用户判断和实际时间。

**第 4 周：盲评与复盘。** 将系统入选条目和随机抽取的未入选条目混合，隐藏其筛选状态，让用户按统一标准标注“值得读/值得试/不相关/证据不足”。检查漏报和来源偏差，微调权重后复跑。试点样本小，盲评主要用于发现问题，不构成独立的效果证明。

### 7.3 预设指标与起始目标

下列目标是试点假设，可根据实际基线改动：

- `Precision@5`：每周前五条中，用户判为值得读或值得试的比例，目标先设 ≥70%；
- `重大漏报数`：试点范围内被独立标为高影响、却未进入任何队列的事项，在预先登记、明确覆盖范围的高影响事件集里，试点目标为 0 起；不能据此推断整个互联网没有漏报；
- `阅读时间`：每周看完精选所用时间，相较基线下降；先设下降 30% 作为可检验目标；
- `证据可追溯率`：重要事实能打开至少一个原始出处，目标 100%；
- `证据夸大率`：摘要中超过证据支持范围的断言比例，逐周下降；
- `行动转化率`：收到的精选中实际进入验证或业务讨论的比例；不追求越高越好，但应看清哪些推荐产生行动；
- `安静日正确率`：系统选择不推送时，抽样确认当天是否确实没有达到门槛的信息。

要特别记录误报和漏报的代价差异：漏掉一个低价值新工具，与漏掉重大安全事故不是同一种错误。将它们混成一个平均准确率，会掩盖高损失事件。

### 7.4 反向测试集

建立一组有意挑选的“陷阱样本”：只有营销标题没有产物的项目、旧版本翻炒、星标很高但不适配业务的仓库、没有许可证的代码、作者自述却被二手媒体写成独立验证、过期教程、重大安全提醒、值得探索的邻近领域信息。用这组样本检查系统能否：挡住夸张主张、不把热度误当质量、识别许可与安全风险、保留真正的高影响事项，以及避免只推荐用户已经熟悉的话题。

## 八、讨论：这套方案的边界

1. **评分仍会出错。** 语言模型会受提示词、上下文和来源可访问性影响；分数必须有解释和出处，不能伪装成客观概率。
2. **证据强不代表业务适配。** 一个经过充分验证的技术仍可能不适合用户的架构、预算和团队能力。
3. **来源覆盖存在盲区。** 搜索引擎、平台 API 与网站策略都会影响可见信息；系统需要显示采集范围和失败情况。
4. **个人画像需要治理。** 用户的业务计划和阅读偏好可能敏感，应减少采集、控制保存期限、允许修改和删除。
5. **自动化权限应逐步放开。** 第一期只读与建议；第二期创建草稿或实验任务；涉及外部发布、付费、客户触达和数据变更时，仍应保留明确审批。
6. **个性化不是永久不变的。** 目标变化时，系统应询问是否调整画像，而不是悄悄沿用过时偏好。

## 九、结论：让系统替人筛选下一步，而不是替人宣布真相

个人信息决策雷达的价值，不在于读完互联网，也不在于给每个项目一个看似精确的分数。它的价值在于持续回答四个具体问题：这件事为什么与我相关？我目前知道什么、还不知道什么？证据在哪里、可靠到什么程度？如果值得进一步投入，最小的验证动作是什么？

本文给出的方案将用户目标、来源采集、证据核验、双轴评分、分级推送、限时验证、状态记录和反馈校准连成一个闭环。它可以先以 Skill + 公开数据源 + 本地状态文件的轻量方式启动，再逐步接入 GitHub、RSS、知识库和定时器。要判断它是否有效，应看用户是否更少花时间在低价值信息上、是否更快找到值得验证的机会、是否能追溯结论依据，以及关键风险是否仍能被发现。

它不是替用户决定“什么是真的”或“该不该做”，而是让每次注意力投入更有依据、每次试验更可控、每次决策更容易复盘。
